# The claim ledger and the asset skeletons (carried inside this skill so it stands alone)

Why: a statement about the buyer side that the seller never gave (what a seat said, saw, agreed, owns or worries about; an "only" or "nobody"; a source the seller did not name) misleads the seller and, inside an asset, the buyer. Prose rules did not stop it; a mechanical check on the exact delivered text does.

## Assets
Every asset written in a buyer's or champion's voice, or written for the buyer to read, starts from `python3 scripts/claim_ledger.py skeleton --type <type>` (champion-email, talking-points, memo, objection-answers, risk-register, forward-note, buyer-email, mutual-plan, seat-map). With no code execution, use the same shapes: the asset shapes in this skill's references, every buyer side line a "[User to add: ...]" slot unless the seller's words give it. Fill every slot the seller's message answers (what the seller offers, the reader, the decision asked, the script's figure, a fact the seller gave about the buyer), in the asset's voice, with the source in the ledger; a slot stays "[User to add: ...]" only when the message gives nothing for it, so a filled asset is usable as a draft. When the seller asks for a number of points or emails, the asset has exactly that number. Add no line about the buyer side outside the skeleton.

## The ledger, on the exact text you will deliver
Every command is written with `python3`; where `python3` is not found (Windows), run it with `python`.
1. Make a folder `.deal-check/` in the current folder. Save the seller's message, word for word, as `.deal-check/user.txt`; each script's printed output in its own file (run the script with `| tee .deal-check/out1.txt`, then out2 and so on); each asset, and every line written for the buyer to read or hear (an email, a note, an opening, a question set), in its own file (`.deal-check/asset1.md`), with the same text inside the answer; and the whole answer as `.deal-check/answer.md`.
2. Run `python3 scripts/claim_ledger.py scan --answer .deal-check/answer.md --user .deal-check/user.txt [--asset .deal-check/asset1.md ...] [--source .deal-check/out1.txt ...]`.
3. For every line marked NEEDS SOURCE, either add one line to `.deal-check/ledger.txt` (`S12 | user | "the seller's exact words"`, or `S12 | script | "the script line, copied exactly"`), or change the sentence into a "[User to add: ...]" slot, a question or a hedge ("may", "worth checking"), or delete it. When the word the scan names (agreed, seen, nobody, only, wants, must, pilot, deadline, told) is not in the seller's words, change the sentence, never the quote. Refer to the seller's facts as "from your message" or quote them; "you told me" or "you mentioned" said to a buyer claims the buyer said it. A worked example in this skill shows the shape of an answer, not lines that skip the ledger. A FIGURE NOT FOUND was worked out by hand: replace it with a script line or remove it. A line about what the seller's product offers or does names only what the seller said about the product: quote the seller's own sentence about it, never the buyer's wish (the buyer wanting Tamil does not make Tamil the offer). A status cell that reports on a seat ("no contact yet", "engaged", "silent") needs the seller's words about that contact; otherwise write "contact not shown". A line that credits items to a named source ("both from the inbound form") names only what that source held, as the seller said it. A risks line names only a risk the seller reported; any other risk is a "[User to add: ...]" slot or a hedge ("may").
4. Run the same command as `check ... --ledger .deal-check/ledger.txt`, saving the answer again after every change, until it prints LEDGER PASS. Every file you save for the seller (an email file, a plan) is also an `--asset`.
5. Deliver: your very last tool call is the same check with `--final` and the same files, with no pipe after it (no `| head`, no `| tee`): `python3 scripts/claim_ledger.py check --final --answer .deal-check/answer.md --user .deal-check/user.txt --ledger .deal-check/ledger.txt [--asset ...] [--source ...]`. When its first line reads `claim_ledger --final: PASS`, your whole reply is exactly the text between its `=== BEGIN CHECKED REPLY <digest> ===` and `=== END CHECKED REPLY <digest> ===` lines: nothing before it (no summary, no "here it is"), nothing after it, no word, line or table changed, and no other tool after it. To change anything, edit the file and run `check --final` again. Write no progress notes to the seller between tool calls. When the seller asks for a change later in the conversation (a shorter email, a warmer tone), edit `.deal-check/answer.md` (and any saved file), run `check` and then `check --final` again; your reply is the new checked text. In Claude Code the plugin's delivery check (a Stop hook) sends you back when the reply is not that text.
With no code execution: list each buyer side sentence with the seller's words beside it by reading, rewrite those without, and write "checked by reading, not by script".
